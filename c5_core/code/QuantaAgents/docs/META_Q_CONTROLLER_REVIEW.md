# 第六版 Q 控制器独立审查

2026-09-06。审查范围为第六版隔离源码中的 `runtime.py`、`ashare_research.py`、`batch.py`、`server.py` 及 `test_meta_q_*`。没有修改业务源码、读取新的行情、调用模型或启动服务器。

结论：固定研究机会、弃权和提交复用的主要路径符合 Q 设计。发现的一个恢复身份问题已修复，**45 项 Q 离线回归和 7 项独立恢复检查全部通过**。在本次审查范围内，没有遗留的可复现控制器问题；这不构成策略生成能力进步的证据。

审查源码摘要和测试清单见 [review_evidence.json](../experiment_traces/meta_q_controller_review/review_evidence.json)。修复后的回归执行了全部 `test_meta_q_research.py` 和 `test_meta_q_batch.py` 中不启动真实 HTTP 服务的用例，**45 passed、1 deselected、15.59 秒**；被排除的一项真实 HTTP 集成由主任务决定是否执行。测试网关是本地替身，不是 Astra 付费调用。初查 31 项通过记录仍保留；修复期间旧测试替身曾有 2 项失败，原因是以 list 评测日志代替真实 splits 字典，作者修正替身后通过。该中间失败回执也保留，生产边界校验没有因此放松。

## 已核实的关键行为

- 动作日程固定为 `D → B → D → B → B → S`。两个 D 只允许事件诊断或 `diagnostic_not_identifiable`，三个 B 只允许组合回测，S 只允许 `submit` 或 `no_supported_strategy`。时隙不可互换；错误动作消费已有付费机会并使运行失败，不能转为额外回测。
- 诊断弃权保留理由、消耗和机会，不执行占位策略。没有受支持策略时输出空分数、`research_unsuccessful=True`；保留批次成员和成本，不把历史最好策略自动补交。
- `_save_raw` 已用有效 64 位策略摘要作为前置条件。`_no_strategy()` 的 `strategy_hash=None` 不再触发回测/原始档案恢复。已执行带 `_evaluation_raw` 的 Cached Case 测试；共用起点加三次 B，恰好四次评测，弃权没有新增评测或终态执行 ZIP。
- `submit` 只接受共同起点或本运行本架构此前成功 B 动作的规范化策略身份；诊断过但未回测、新策略、失败回测、另一架构已有策略均不能获得提交资格。提交和开发期最终复核复用同一证据，不新增策略评测。
- 已保存的研究记录校验顺序、响应/观察摘要和预定动作。付费回执的复用必须匹配提示词并通过当前 schema；固定日程禁止 `retry` 和同一时隙更换提示词再付一次费。暂停在模型返回后、研究观察保存前，重启仍只使用原来的六次调用。
- schema 3 保存共同行动日程、提交政策、数据门槛版本以及双方共同的执行诊断开关。成员或服务不匹配时批次停止，GET 恢复不会变成另一次 POST；未知创建结果保留原请求键，不能因未观测到而重发。
- 两题各一次重复按 `ABBA` 排序，四个 arm 合计 24 次研究调用。Q 默认每 arm 六次、最多一次尝试、硬预算 600,000 token；批次总事故额度 2,400,000 token，每成员预留 600,000，最长 57,600 秒。软提醒不会自行缩减已经冻结的研究机会。网关的使用量报告存在时间粒度，因此额度是现有控制器的事故停止机制，不是供应商逐 token 的强制账单上限。
- 已保存执行诊断报告可直接按摘要复用；报告丢失、缓存为空时仅恢复同一冻结策略，并比对完整观察和原报告内容摘要；已有报告被修改则拒绝覆盖。这一条已由作者修复且相关测试通过。

Cached Case 用来覆盖真实 `_evaluation_raw` 分支，但其表是最小测试表，没有验证完整市场经济计算；真实开发数据 fixture 与执行诊断模块的财务回归属于另外的验证范围。

## 已修复的 P2：丢失的执行 ZIP 会改变原冻结身份

原问题位置：`ashare_research.py::_save_raw` 在已登记 ZIP 不存在时进入重建路径。初查版本仅在文件已经存在时与旧登记 SHA 比较；重建采用 `ZipFile.writestr` 默认的当前时间，随后无条件用新 SHA 替换旧 artifact 条目。

这在正常恢复中即可触发：原 ZIP 因意外丢失，过一段时间恢复，三张 CSV 的内容完全相同，但 ZIP 元数据时间不同，整个压缩文件 SHA 随之改变。旧冻结摘要被悄然替换，外部审计或引用原摘要的结果失去一致身份。此问题不是额外模型调用，也不必然改变收益，但会破坏“恢复只复用原证据”的来源保证。

独立复现 [zip_recovery_repro.json](../experiment_traces/meta_q_controller_review/zip_recovery_repro.json) 使用真实 `_save_raw`、带 `_evaluation_raw` 的内存 Case，以及独立审查目录的生成文件。没有触碰任何原实验档案：

| 检查 | 观察 |
|---|---|
| 首次生成的 ZIP SHA | `7e8eb9ac26f0642a86f210eb0b994b7dac353051a4d4278961434ca10e4eef76` |
| 丢失后重建的 ZIP SHA | `a1b672cb87ce7312edacb387632253ebffb7f91f71388410085c5af42f315189` |
| 三个 CSV 成员摘要 | 逐一相同 |
| 恢复拒绝 | 否 |
| 恢复后的 artifact 登记 | 被改成新 ZIP SHA |
| 新模型调用 / 行情读取 / 回测调用 | 0 / 0 / 0 |

原修复建议：首次写入 ZIP 时固定成员顺序和元数据，丢失后重建必须与原已登记 SHA 一致才重新登记。对旧的非确定性档案，无法恢复相同摘要时应保留明确失败，或通过独立、可追溯的修复事件保留旧身份与新重建身份；不能静默把原冻结条目改为新文件。

作者已在隔离第六版修复。成员日期固定为 `1980-01-01`，权限、压缩方式和 CSV 换行固定；重建仅当候选文件摘要与原登记相同才正式恢复。不一致时保留原登记及单独候选文件，记录拒绝事件，不冒充原证据。

独立复验脚本只使用审查目录生成的账表和真实 `_save_raw`，并以实际 `build_execution_diagnostics` 生成报告，没有修改业务源码。证据为 [fix_verification_20260906T132459444342Z.json](../experiment_traces/meta_q_controller_review/fix_verification_20260906T132459444342Z.json)，对应 `ashare_research.py` 摘要 `60b5ccad8b6c0ea3a0518cdaa6ab60ca3952315605ecd23a8cd598158cde6320`。

- 改变 ZIP 元数据时钟后，同一 raw-cache 重建得到同一摘要，不重新回测。
- raw-cache 账表变化及旧非确定性 ZIP 均拒绝重建覆盖，原登记保持不变。
- 已有完整诊断报告在 raw-cache 为空时经过语义核验后复用，不重新回测。
- 报告丢失后仅恢复同一冻结策略，重建报告摘要与旧登记一致，并有恢复事件。
- 报告摘要与外层观察不一致时，即使更新了报告内部摘要和 artifact 登记摘要，仍被语义关联检查拒绝。
- 报告来源摘要与冻结 run/case 不符，在档案使用前拒绝。

7 项检查通过；其中第二条包含两个独立场景。原始失败复现和修复后证据分别保留，没有用成功结果覆盖失败记录。

## 两问自检

**这一步做得怎么样？** 已把六步机会、弃权、已有策略提交、付费回执恢复及 ABBA 预算逐项对照源码与离线用例，确认覆盖 `_evaluation_raw` 分支；发现的恢复摘要身份问题已有原失败证据和独立修复复验。

**下一步该做什么，如何改进？** 由主任务运行真实开发数据零模型 fixture，然后开展单独冻结的 Q 研究竞赛。Q 的架构价值须随后通过冻结研究竞赛检验，不能以控制器测试通过推断生成策略的能力。
