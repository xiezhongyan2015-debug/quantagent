# 固定 8 股历史公司行动来源试点

2026-09-06。结论：**已经找到可批量补充历史事件候选的入口，并实际取得 2017–2021 年 37 条索引记录、7 份详情；尚不能据此生成完整、已核验的公司行动现金/股份账。** 未修改主源码、revision3/4、运行计划或交易输入。

## 固定范围与实跑证据

样本沿用 L2 审计按代码哈希选定的 8 股：600006、603786、600653、600741、002296、002377、002576、002527。没有因分红多少、事件类型或收益替换股票。本次不读价格/收益，不打开最终行情，不调用研究模型。

采集前冻结规则为：提取索引中**公告日期**在 2017-01-01 至 2021-12-31 的全部可见记录，保留实施、预案、不分配等原始状态；每股选择该窗口内公告日期最早的一条“实施”分红记录取详情，同日按事件类型、源行号打破并列。没有实施行就不选替代事件。公告日期窗口不等于按财报所属年度或除权年度计算的完整事件覆盖。

实际请求 **18 次，耗时 21.438 秒**：AKShare 官方说明 1 次、历史索引 8 次、详情 7 次、固定前两股的巨潮证券身份查询 2 次。16 次取得内容，2 次 HTTP 500；两次失败均未重试。最大单源 3,284,441 字节，总保存 4,126,597 字节，均低于预定 30 请求、单源 8 MiB、总网络时限 5 分钟。

所有源的 URL、请求/完成时间、HTTP 状态、内容类型、字节数、SHA256 和错误见 [sources.json](../experiment_traces/meta_corporate_action_pilot/sources.json)。网络请求在独立子进程执行，父进程实施每请求和总时限，禁用重定向与失败重试；HTML 不执行脚本或资源请求。

## 详情补出了什么，仍缺什么

[AKShare 官方说明](https://akshare.akfamily.xyz/data/stock/stock.html)列出 `stock_history_dividend_detail(symbol, indicator, date)`，其中 `indicator` 区分分红/配股，`date` 可定位具体事件详情。此次直接保存源页面，没有安装 AKShare 或把第三方说明误当原公告。已保存该接口的[独立说明摘录](../experiment_traces/meta_corporate_action_pilot/akshare_interface_excerpt.txt)及来源哈希。

| 代码 | 索引公告日 | 股东大会决议公告日 | 登记日 | 除息日 | 混合标签起始日 | 索引税前现金 / 10 股 |
|---|---|---|---|---|---|---:|
| 600006 | 2017-07-10 | 2017-05-19 | 2017-07-13 | 2017-07-14 | 2017-07-14 | 0.33 元 |

例如 [600006 的固定详情](https://vip.stock.finance.sina.com.cn/corp/view/vISSUE_ShareBonusDetail.php?stockid=600006&type=1&end_date=2017-07-10)和 [603786 的固定详情](https://vip.stock.finance.sina.com.cn/corp/view/vISSUE_ShareBonusDetail.php?stockid=603786&type=1&end_date=2020-05-29)实际提供了不同于索引公告日的股东大会决议公告日。二者不能混为首次预案发布时间，也不能以 2026 年采集时间充当历史可得时间。

本次提取的是 `sharebonusdetail` 事件表，已排除导航、报价等页面区域。可直接实现的字段边界如下：

| 字段 | 本次证据 | 可用方式 |
|---|---|---|
| 登记日、除息日 | 7/7 详情与对应索引一致 | 保留为二级来源候选，并保留两处原值用于核对 |
| 每股税前现金 | 历史表头明确“每 10 股”；详情报价值与索引金额一致 | 可以精确除以 10 生成候选；如 600006 是 0.033 元/股，不能把 0.33 当每股金额 |
| 现金派发日 | 7/7 只有“红利/配股起始日（送、转股到账日）”的混合标签 | 暂存 `ambiguous_distribution_start_date`，已核实派现日保持 null，不因等于除息日就直接开放现金 |
| 送股与转增 | 索引分别显式为 0，所选详情相应字段为 `--` | 保留索引零与详情缺失的区别，不能把 `--` 自动转 0 |
| 红股上市/股份可卖日 | 所选 7 份详情上市日均空，且没有正送转事件 | 不能检验该源对有送转事件的上市日覆盖；不把现金分红样本的空值泛化为全站缺失 |
| 原实施公告发布时间 | 目前只有索引日期和股东大会决议公告日 | 原公告核验字段为 null；历史公告链和盘中时间仍需原文 |
| 配股认购/缴款/上市 | 历史索引无可见配股行；详情有相关字段但全空 | 保持未覆盖，不用分红起始日补认购期或上市日 |
| 账户税负 | 7 份详情的“税后”数都等于“税前” | 不能据此认定账户免税；税负取决于账户类型、持有期与适用规则，相关核验字段保持 null |

规范化候选见 [selected_event_candidates.json](../experiment_traces/meta_corporate_action_pilot/selected_event_candidates.json)。每条均为 `usable_as_complete_ledger_event=false`；已核实派现日、股份可卖日、原公告日期和账户税负均未伪造。

## 原文入口失败如何保留

采集前固定对前两股 600006、603786 尝试巨潮证券身份入口；两次均返回 HTTP 500，原响应已保存。因此没有取得它们的 orgId，没有继续发送公告列表或 PDF 请求，也没有换另一只更容易成功的股票。此结论只针对这次具体请求，不能推出巨潮没有历史公告或整个数据源不可用。

本固定样本的原公告核验仍是 **0/7 个详情事件**；官方入口尝试保留为 **0/2 成功**。先前[平安银行/安集原文来源试验](META_CORPORATE_ACTION_SOURCE_FEASIBILITY.md)证明别的历史发行人入口可以获取原文，但它们不进入本固定 8 股试点的成功分母。

## 下一步可以直接实现的工作

1. **先交付可复用的事件索引适配器。** 直接以本次 37 行和原始 HTML 作为回归夹具，产出独立的 `index_events` 与 `coverage_by_stock_year`。事件保留股票、公告日、类型、进度、原始每 10 股单位、源 URL/哈希/采集时刻；版本关系另表维护，不能简单按财年去重或只留实施行。清单中的未知年份继续占分母。
2. **补两个确定的原文核验任务。** 在新的有界任务中，仍固定 600006 的 2017-07-10、603786 的 2020-05-29 两个实施索引日，先依据发行人/交易所的可用公告目录或核实过的证券身份映射定位原 PDF。不要猜 orgId，也不要无限重试失败接口。需返回原文公告日期、派现安排、适用账户、税项、以及是否明确无送转；失败继续留在待核验队列。
3. **把候选解析与账本激活分开。** 当前已有稳定入口产出税前现金、登记日与除息日候选；只有公告安排核验通过、事件覆盖门和账户规则通过后才生成可激活账本事件。若只能确定日级派现安排，可在后续方案冻结“下一交易日才使用该现金”等仿真假设，同时保持“公告安排/仿真入账/真实交割观察”三者分开。此次没有应用任何入账假设，也没有计算收益。
4. **覆盖扩展要有单独验收。** 为这 8 股补证券存续期与公告版本索引，解释 3 个未观察单元，并核对预案、更正、撤销等状态链。正送转、配股等机制另设预先声明的功能验收样例，不能拿它们替换这批固定样本或声称本批已经覆盖相关机制。全市场采集应在这套小样本契约稳定后按清单扩展、逐源缓存、保留失败。

## 可复现与两问自检

采集脚本为 [audit_historical_corporate_actions.py](../scripts/audit_historical_corporate_actions.py)，输出目录为 [meta_corporate_action_pilot](../experiment_traces/meta_corporate_action_pilot/)。计划已存在时脚本拒绝重复采集；`--summarize-only` 只重算本地文件。原采集版本归档为 `collection_script.py`，与 plan 的 SHA256 一致；提取器修订后的哈希单独记在 result 中。

[离线验证](../experiment_traces/meta_corporate_action_pilot/validation.json) **9 项通过**：固定样本、脚本/来源哈希、全部网络边界、无重复请求、状态与失败分母、首条实施选择、每 10 股换算、缺失字段不补零、缺表不冒充无事件。验证本身没有网络、价格或模型调用。

**这一步做得怎么样？** 已把“也许能补历史事件”推进到固定 8 股、可复算的 37 行候选和 7 个详情入口，并发现具体字段语义与原文入口问题；没有因为取得详情就宣布执行账完整。

**下一步该做什么、如何改进？** 将这些原始页面固化为事件适配器测试，先补固定的两个原文任务，取得明确派现安排后再衔接隔离股份账。仍保持事件覆盖与正式执行门为 false，原有策略结果不重写、不晋升。
