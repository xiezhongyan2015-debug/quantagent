# 已保存工具结果的可见性与中断恢复

本轮把已经完成、却被随后费用写入异常遮住的工具结果接回普通研究入口。已有失败仍保留为失败；模型历史另行显示原错误和经过校验的原始结果。已保存结果可以继续用于证据查询及开发报告，恢复不重新运行账户或工具，也不证明金融有效性。主控验证已完成，checkpoint 031 待独立复核。

## 问题与实现

原路径中，工具先保存 request/result/artifact 和原始计量凭据，再将费用写入派生账。最后一步异常会覆盖生产器原返回值：普通工具进入 failed，只剩错误；已有 workbench 的资金执行则暂停在 applying。另一个进程中断窗口会留下完整原始返回凭据，但没有 application.json，原恢复入口仍无法使用它。这三种反例均先在新生成的范围中保存失败证据，再作修改。

新增 `src/quanta_agents/meta_v3/saved_tool_results.py`，读取同一注册根目录、study、trial、task、模型调用和工具请求的权威计量。必须是原始 outcome=returned；再次核对模型 intent/proof、请求、结果哈希、artifact 哈希，以及计量清单中每个原输出文件的路径、字节数和 SHA256。本地计量副本不能替代共享原凭据，raised 生产器的残留文件不能升级为结果。校验不会重跑生产器、扫描行情或重算收益。

`ResearchRuntime._history` 对当前任务的 failed 行生成只读视图：status 仍为 failed，原错误在 original_application_result，result 为校验通过的原输出，saved_result_recovery 说明来源及限制。提示上下文保留这些标记；原数据库行、application.json、费用和已导入的旧历史均不改写。

对于当前调用已经有完整原始返回证据、随后发生费用写入异常的情况，运行器保留 failed 应用记录，让上述视图提供结果；未知或损坏的子执行仍暂停。对于 applying 且 application.json 尚未保存的中断，只有原始返回凭据及全部输出通过校验才补写原调用的应用回执并完成应用；不存在既有 failed 行可被改写。已存在的独立暂停不会自动解除。冻结源码约束仍在，旧付费范围不能用新代码直接续跑。

## 保存的验证

共 30 次用例执行、26 个唯一用例，26 个唯一用例的最后一次结果均通过。具体为：首轮修前 2 次失败；首轮修后 21 次中 20 通过、1 次测试夹具失败；定向 3 次通过；额外进程中断反例修前 1 次失败、修后定向及受影响恢复检查 3 次通过。不能写成“30 次通过”。夹具失败仅因把两次实时 now_epoch 要求完全相等，修正为状态不变式后只重跑该用例。首次日志显示另遇 Windows GBK 编码错误，发生在 pytest 完成后；原始字节日志和 JUnit 均保留，读取证据时没有因此重跑。

新范围预先上限为 40 次用例、3 次生成账户执行、0 次真实模型及真实/密封数据读取；实际 30 / 3 / 0 / 0。三个账户执行分别属于修前、修后的资金路径和受影响的既有应用回执中断回归；它们不是三个独立研究样本。恢复各原账户均零重跑。修前源码正文、两个实现版本、测试修订、失败原件和输出均直接归档，验证清单含 477 个文件。

资金路径使用两只生成股票、12 个交易日和 10,000.00 元完整初始现金。同一工具执行在费用投影异常后保留 failed，成本恢复后后续公开 inspect_execution 读到原 4 笔成交，并通过 submit_research_report 提交生成的 strategy_for_development 报告。最终现金 9,955.15 元，净损益 -44.85 元，账面费用 26.85 元；不把全部损失解释成费用。原资金文件哈希不变，工具候选次数仍为 1。该路径的三张模型回执合计 60 个**生成测试 token**，没有实际模型调用；终稿不是 Astra 的真实回答。报告只表示合法开发提交，execution_valid 和 formal_target_success 仍为 false。

拒绝检查包括请求/结果/artifact 篡改、本地模型回执改写、原始失败回执改写、原计量缺失、raised 生产器残留、未知子执行、原输出在费用异常时发生漂移、无原始计量的 applying 中断及独立暂停保留。原费用恢复的 10 个用例和受影响的已有恢复路径也通过；没有重复运行已通过的账户种子来美化结果。
