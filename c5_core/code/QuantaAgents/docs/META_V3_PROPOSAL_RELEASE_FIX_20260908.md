# 第021阶段提案放行门控修复

父任务提出的021-C01和021-C02均在隔离的生成夹具中复现并完成修正。14项新定向检查由修前12失败、2通过变为修后14通过；另两项受影响的原有检查通过。此结果待父任务独立复核，不代表模型身份已确认、策略成功或完整架构比较完成。

021-C01：原检查信任派生的`control_release.allowed`。仅修改这一位可以越过检查；连同重新计算摘要一起篡改汇总身份、调用列表或候选状态也未被原检查发现。现在封存和放行共同使用只读重建函数：逐次重放原始网关完成证据，核对调用身份、用量、注册候选和费用，重建整份提案收据。放行前必须同时匹配收据、封存意图及重建的放行记录，并且所有调用的运行时身份确认必须严格为True。

021-C02：固定/随机入口原来以绑定文件当前是否存在决定是否检查模型提案。现在`requires_model_proposal`在创建控制计划时冻结，并进入计划摘要；提案入口显式设为True。控制入口依据计划选择模式，必需绑定缺失、意外添加绑定、绑定与计划或路径不符，以及缺失模式字段的旧格式均拒绝。旧封存计划不迁移、不回写、不重新执行；独立的生成数据控制计划显式记录False。

验证仅检查门控，测试内禁止模型、批执行和子进程。修前固定/随机缺失绑定反例到达预先放置的来源检查哨兵即停止，没有运行账户。修后同一批14项测试文件保持逐字相同，全部通过。确认的生成收据夹具只证明门控机制，不是供应商身份凭证。
