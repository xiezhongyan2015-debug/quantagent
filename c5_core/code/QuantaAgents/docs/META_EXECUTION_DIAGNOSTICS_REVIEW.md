# V6 执行诊断独立审查

日期：2026-09-06。主要对象为 `meta/execution_diagnostics.py`、`meta/ashare_case.py` 的诊断接入及恢复控制器 `_save_raw`。先进行只读独立审查，随后按父任务明确授权修正模型可见列表的大小边界；没有修改其他 agent 所有的恢复控制器。

**会计桥接和正常 case 接入通过独立检查。模型可见列表已限制为固定前 N 个样例，52 项定向测试通过，诊断模块已冻结供集成。恢复控制器的语义关联修复也通过独立 12 场景复测，修前失败证据完整保留。** 这些结论验证工程与证据边界，不构成策略收益或架构改进有效性的证明。

## 1. 独立现金与成本路径

使用 Decimal 独立构造 7 个归档交易日、10 个订单、2 个合成股票。保留一个亏损闭合持仓段、一个盈利闭合段和同日清仓后重新买入的右删失持仓段，不访问模型、网络或新行情。

固定初始现金 20,000 元，逐订单现金公式得到：

| 项目 | 元 |
| --- | ---: |
| 期末现金 | 19,644.00 |
| 期末持仓市值 | 264.00 |
| 期末总资产 | 19,908.00 |
| 净 PnL | -92.00 |
| 全部费用 | 16.00 |
| 全部滑点 | 60.00 |
| 同一已成交路径的参考价格 PnL | -16.00 |
| 已实现净 PnL | -82.55 |
| 未实现 PnL 变化 | -9.45 |

每个归档日以及跨年汇总均核对两条恒等式：

```
净 PnL = 同成交数量路径参考价格 PnL - 费用 - 滑点
净 PnL = 已实现净 PnL + 未实现 PnL 变化
```

加仓的加权成本包含买入成交价和买入费用；卖出已实现 PnL 扣除对应加权成本及卖出费用。未实现 PnL 用总持仓市值减剩余总成本计算。日末净资产与现金、总持仓市值，以及当日订单费用/滑点/成交额/数量均对账，没有再次从已实现 PnL 重复扣费。

两段完整持仓的净 PnL 分别是 **-129.10 元与 +49.60 元**。重新进入的未闭合段保留剩余成本 273.45 元，逐股未实现 PnL 仍为 null。所有 7 日、全部 10 个订单及正负持仓段留在分母。把一个已实现成本字段改错 0.01 元会被拒绝；confirmation 标签也被拒绝。

独立证据：`experiment_traces/meta_execution_diagnostics_review/review_v6/plan.json`、初版 `accounting_result.json`，以及最终有界版本复核 `bounded_accounting_check/accounting_result.json`。后者绑定最终诊断源码 `bfb496…`，没有覆盖先前结果。

## 2. 持仓段、右删失及 T+1 含义

同一股票连续非零库存期间，加仓和部分卖出属于同一个持仓段；库存归零后再次买入创建新段，即使发生在同一归档日期。本独立路径分别验证了两次加仓、三次部分减仓、两个完整退出，以及新的右删失段。完整段持续 3 和 2 个归档会话，右删失段已观察 2 个会话。

右删失段没有虚构退出日、最终净 PnL 或完整持有期；仍提供已实现部分与剩余成本。会话数来自归档 daily 表，程序明确没有独立核实完整交易所日历，不能把存在日期标签当成日历完整性证明。

当日卖出累计数量超过当日开盘前已有的调整单位库存时，相关订单被标为涉及当日新买单位。在独立路径中准确标出第 6 号来源订单。它是**调整单位算术检查**；原股份、公司行动、送股上市日和可卖账户库存不在此诊断中，因此 `execution_valid` 保持 false。不能用这个标记宣称已核实真实 A 股 T+1。

## 3. 能解释的内容及不可识别部分

同成交路径加回费用/滑点，仅是会计加法。原模拟的数量、入场、现金分配和后续决策已经受成本影响，不能把加回后的数值标成无摩擦策略收益或重新计算一个无成本 Sharpe。本模块保留该解释，也没有输出所谓无成本策略 Sharpe。

归档只含总持仓市值，逐股日末价格与完整持有库存的开收盘标记并不齐全。因此逐股每日浮盈亏、隔夜/盘中分解、最大有利/不利波动、价格陈旧原因均保留为 null。拒单、涨跌停未成交、停牌、容量、队列、行业/风格归因也没有从实际成交或目标权重猜出来。完整原始订单能够支持逐股已实现成本与持仓段记录，但不能弥补缺少的日末市场观测。

## 4. Case 接入与缓存

使用项目既有合成市场 fixture，在实际 `AShareCase` 上统计市场读取和回测调用：

- 开关默认 false，只接受显式 boolean；字符串、整数和 null 拒绝。
- 开启前后，普通回测的 score 和全部 metrics 完全一致。
- 首次开发回测生成诊断；getter、相同策略缓存命中均为 **0 次额外市场读取、0 次额外回测**。
- 未计算的策略或改变后的策略不能借用其他缓存；报告含同一 strategy/data/source 哈希。
- 返回值与缓存分离，修改返回的 table 不影响后续 getter。
- confirmation 回测不附诊断；final 在读取数据之前被封存门拒绝。测试用到的 confirmation 也只是合成 fixture，没有读取真实确认期/最终期行情。
- 模型观察仅含 scope、identity、integrity、summary，完整 tables 通过单独报告接口返回。

该次构造的诊断 source hash 与从当前 `Engine.source_manifest` 提取的原算法一致。复核没有启动 Engine、数据库或 worker。证据为 `case_result.json`；总共 3 次有意安排的合成回测是关闭开关的开发回测、开启开关的开发回测和合成 confirmation 回测，不能误称成 getter 触发三次查询。

## 5. 已修正的模型上下文大小边界

只读审查发现原模型可见 integrity 带完整同日卖出违规序号列表，summary 带全部右删失年龄。父任务随后明确授权修改这个模块。

最终版本递增为 **`execution_diagnostics_v2`**：

- 同日违规序号只给固定 `chronological_examples` 个最早样例，保留完整总数、样例上限和省略数量；全量序号放在 `tables.same_day_inventory_violation_order_ordinals`。
- 右删失年龄只给最早 N 个样例，新增基于全部右删失段的桶计数、最小/最大值及分位数。全部持仓段继续保存在 `tables.spells`，没有为限制上下文而删除分母。
- N 使用已经存在的冻结策略参数，默认 3、最大 10，允许 0；样例按时间顺序选取，不按盈亏筛选。

新增测试构造 **20 个同日违规订单、12 个右删失段和 20 个闭合段**，分别检查 N=0/2/3/10。每种设置均保留全部 52 个订单、32 个持仓段、全量违规序号与右删失分布，模型列表长度严格受 N 限制。这里解决的是两类随事件数量增长的列表，整体提示词大小仍需由上层 harness 管理。

最终验证：三组诊断、case 接入与大小边界测试 **52 passed in 9.46s**，JUnit 用例耗时合计 9.395 秒；独立 Decimal 会计路径在最终源码上再次通过。

冻结源码 SHA256：`bfb496de608691a9cde916b991a4c721e94b82b2cab4ed4dc2309bbff2b8d1b1`。新增测试 SHA256：`78ef32053049b1c49ffa5ca3677307df6f43c75f9384113f18a9ca7cc0944bc9`。冻结标记为 `bounded_change_receipt.json`，只冻结本模块与相关测试，不代表其他 agent 的 V6 文件已完成或正式策略目标已达成。

## 6. 恢复审查发现及边界

最初恢复分支在 execution.zip 已存在时跳过重新求值，但随后仍向新建 Case 的空内存缓存请求完整诊断，导致 `no completed development execution diagnostic`。控制器所有者已改成优先复用有登记哈希的报告；缺报告时重算原策略并要求完整 observation 相同。

父任务明确允许这种**原策略、原冻结数据、完整观察必须一致的确定性重放**；它需要单独恢复事件且不能增加研究搜索机会，也不能调用模型。它和正常 getter 的“0 次额外回测”是不同路径，报告分别计数。

修前独立 12 场景保存在 `recovery_before_semantic_fix/result.json`，绑定控制器 SHA256 `26e401f6a008561a5e6dc3998841d3baabd88d32cf62d0ec27cef84814d2b7e4`：

- 正确已登记报告复用，0 次重算；缺报告及未登记但内容正确的报告按同策略重建，1 次。
- 重算观察不一致拒绝，未写出诊断报告。
- 已登记后篡改的报告或 ZIP 被哈希门拒绝，原 ZIP 未覆盖。
- 但是，**内容哈希登记正确、语义归属错误**的报告仍被接受：错误 strategy/data/source、错误 summary、外层 observation.datahash 错误以及请求策略与观察策略不同，共 6 种。

该问题由控制器所有者补齐请求策略、观察、报告 identity 与四部分模型证据的完整关联。哈希只说明当前文件等于登记文件，不能单独证明文件属于该策略/数据/观察。

修后独立矩阵使用冻结控制器 SHA256 `60b5ccad8b6c0ea3a0518cdaa6ab60ca3952315605ecd23a8cd598158cde6320`、最终 V2 诊断报告及完整的合成 run.config.source_manifest / expected_data_snapshot / prepare.packet 身份形状。12 场景均达到预期，结果保存在新的 `recovery_after_semantic_fix/result.json` 与 `verification_receipt.json`：

- 原先错误接受的 6 类语义不一致全部拒绝，均未重算。
- 正确已登记报告只复用，0 次重算，记录 `diagnostic_artifact_reused_verified`。
- 缺报告及未登记但内容正确的报告各恰好重算 1 次原策略、原 split；完整 observation 相等之后才登记报告。恢复开始、观察校验与报告登记分别留事件。
- 重算观察不一致时拒绝，记录拒绝原因，不写诊断报告。
- 已登记报告和 ZIP 的字节篡改仍被拒绝，全部场景的旧 ZIP 字节均保持原样。
- 所有恢复事件明确 `model_calls=0`、`search_opportunities_added=0`。Case stub 的 evaluate 明确断言原规范化策略和 development split，使用固定内存数据；复核没有访问模型、网络或行情。

据此，缓存恢复与上述 6 类语义归属发现关闭。复核脚本记录矩阵运行前后控制器 SHA 相同，没有修改 V6/src 或修前证据。本矩阵不覆盖 ZIP 缺失后的重建字节一致性；该项由其他独立审查验证，不能混入本矩阵的 12 场景计数。

直接从 CSV ZIP 重新生成报告，也不能仅凭经济数值近似相同就覆盖原 observation：导入后的类型、浮点细节、帧哈希以及 ZIP wrapper 的附加身份字段都可能改变完整报告。当前独立试点只证明其经济桥接仍成立，没有把两个完整 JSON 不相等误判为完全可互换。

## 两问自检

**这一步做得怎么样？** 用独立亏损路径核实逐日成本与持仓账，并实际发现恢复缓存和语义关联缺口；获授权后修正模型可见无上限列表，52 项测试和最终源码独立经济复核通过。恢复语义修复的独立 12 场景复测也通过，修前错误证据没有覆盖。没有把会计自洽称为原股份执行有效或 Sharpe 目标达成。

**下一步该做什么，如何改进？** 将本审查纳入全包源码冻结后的真实开发数据 fixture 与联合回归验收，另核对其运行证据。原始报告、失败和重放事件分别保留，模型只获得原研究机会所允许的观察；随后再评估它是否改善研究判断，不能仅用新增诊断字段或测试通过宣称架构有效。
