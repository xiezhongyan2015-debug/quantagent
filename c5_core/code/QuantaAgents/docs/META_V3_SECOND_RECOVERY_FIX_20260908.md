# 二次中断后的原始结果校验

主控已复现并修复父任务预告的 031-C01。修前四种二次恢复变体都被接纳为 applied；修后同样四种全部拒绝，原调用保持 applying，工具费用不变。完整未变的回执可完成一次并幂等读取。17 次用例执行包含修前 4 次失败和修后 13 次通过，覆盖 13 个唯一用例。本阶段待父任务独立关闭，不表示金融验收。

## 根因与修正

031 在 application.json 不存在时核验原始 returned 结果，再保存应用回执。但若保存后、finish_apply 前再次中断，下一次恢复会因文件已经存在而绕过完整校验，仅比较模型响应及 artifact_hash。修改原 request/result 文件，或者保留 artifact_hash 却改写 application.result.public，都可漏过该分支；删除 saved_result_recovery 标记也不能成为合理的降级理由。

`saved_tool_results.verify_application_result` 现在根据冻结的 canonical 计量协议决定校验要求。当前协议下，非终稿成功应用的每次恢复，都必须重新取得原始 returned 凭据，核对其模型/任务/请求绑定和清单内所有原输出，并要求完整 application.result 与原结果相同。调用位置在 `runtime.py` 的已保存成功应用恢复分支，和回执是否有恢复标记无关。

已有工具计量但属于未标记旧协议的范围仍只读；本轮没有迁移旧范围。没有集成工具预算的早期基础路径保留原有应用回执恢复行为，夹具只验证该兼容分类，不证明旧付费范围可在新源码下续跑。原冻结源码检查继续生效。

原生产器没有可信 returned 凭据时，不能靠本地文件或伪造成功应用回执补成成功。当前协议下，批量路径如果只能从子结果重建新输出而没有原始 returned 锚点，也不能经这个成功恢复入口完成；为此类派生恢复另建可信回执的工作尚未实施。这里未新增账户重放或自动重试。

## 证据与边界

冻结范围为 `validation/saved_result_second_interruption_001`，上限 32 次用例、零真实模型、零账户/策略执行、零真实或密封数据读取。实际用例 17 次，其他三项均为零。清单含 282 文件，保存修前测试全文、源码、红/绿日志与 JUnit、每种状态变化及费用快照。未因复核重复运行已关闭账户或模型。

四个红/绿反例分别是原 request 输出漂移、原 result 输出漂移、派生 application.public 漂移，以及删除恢复标记后的同类漂移。每个版本的各变体均使用自己的生成 inspect_inputs 调用，原模型回执为显式生成的 20 token。生产器仅在准备该变体时执行一次，两次恢复均不重跑。它们不是真实供应方调用，也不是独立研究样本。

其余检查包括保留/移除标记时的未变回执幂等成功；没有恢复标记的普通应用回执仍采用相同原始校验；raised 生产器的残留文件不能通过改写 failed 标记成为成功；缺失原始计量不能依赖已有应用回执；未集成工具预算的兼容路径；031 的有原始 returned 中断恢复、无计量中断拒绝及原 failed 历史视图三个受影响用例。最终均通过。

031 的 477 项已封存验证文件和原真实提案的 75 文件保持原样；031 固定交接材料中 20 项不变，只有 runtime.py 与 saved_tool_results.py 两项源码按本轮预先保存的原版本改变。项目八个供应方账本仍为 57 次调用、1,427,801 已知 token、0 未知预留，生产 canonical study registry 仍不存在。平台主控/审查消耗另记，不能与供应方账本相加。

本轮原定的整轮资源计量因这一真实复核缺陷而后移。尚未实现初始化、提示构建、结果校验、独立控制入口及子进程的完整资源账；实际逐调用模型身份、真实数据/执行/容量准入、跨案例独立重复、冻结样本外及新增前瞻验收也未完成。正式成功分母仍为 0，目标保持 active。

后续若出现第二次恢复不再核验原始返回、移除标记即可降级、派生结果可与原结果不一致、恢复改写成本或重跑生产器，应重开 031-C01。下一步继续整轮资源计量及真实研究准入，不能用测试数量代替策略研究结果。
